## Key Findings

### CRITICAL
1. returns.rs:146 — `list_documents(USERS, Some(1000))` unbounded fetch to find admins. Runs on every return escalation.
2. returns.rs:195 — N+1 loop: `for admin_id in &admin_ids` calls `query_bind` (push token lookup) per admin. Should be a single IN-clause query.
3. cron/mod.rs:1250 — `LIMIT 2000` orders fetch for seller metrics (30-day window, no seller filter). On 8GB VPS with many orders this materializes the whole dataset.
4. cron/mod.rs:1413 — `LIMIT 5000` products fetch for trending computation.
5. cron/mod.rs:2160/2228/2288/2330/2385/2439 — Multiple `SELECT * FROM payouts` with NO LIMIT in test helpers (query_raw format! pattern).
6. warehouses/mod.rs:555 — `SELECT * FROM warehouses WHERE parent_id = '{}'` with no LIMIT in test, unbounded.

### WARNING
1. addproduct_submit_section.dart:289,321 — `List.generate(...)` used instead of `ListView.builder` for variant option cards and variant rows. For small lists (<10 items) acceptable, but no upper bound enforced.
2. addproduct_submit_section.dart:263 — `ref.read(sellerWarehousesStreamProvider)` inside `_handleSubmit` is correct (one-time read), not a rebuild issue.
3. add_product_viewmodel.dart:219 — `price * 100` uses double multiplication before `.round()`. Acceptable per codebase convention (display layer converts).
4. indexes.rs — Missing indexes on `orders` for `buyerId`, `sellerId`, `orderStatus`; `warehouses` for `parent_id`; `_push_tokens` for `user_id`. These are the most-queried fields in the changed handlers.
5. digital/mod.rs:1448 — `SELECT * FROM software_access_tokens` with no LIMIT or WHERE (test helper, but pattern is dangerous if copied to prod).
6. native_triggers.rs — Dozens of `list_documents(NOTIFICATIONS, Some(10-50))` calls. Bounded but not indexed on `userId`.

### OK
1. rest_api.rs — `get_products` and `list_orders` both use parameterized `LIMIT $limit OFFSET $offset` with `.clamp(1, 100)`. Safe.
2. add_product_viewmodel.dart — No API calls in build(), provider is `autoDispose` (correct for a form ViewModel).
3. addproduct_submit_section.dart — Submit calls `ref.read()` not `ref.watch()`. No accidental rebuild trigger.
4. sellerWarehousesStreamProvider — `StreamProvider.autoDispose`, re-fetches only on dispose/re-entry. No polling interval.
5. coupons/mod.rs — All coupon queries use `LIMIT 1` lookup by code. Efficient.
6. returns.rs:445, refunds.rs queries — All use `LIMIT 1` point lookups. Efficient.
7. cron/mod.rs — Most cron queries are bounded (LIMIT 50-500). Dangerous outliers are LIMIT 2000/5000.

**Why:** 8GB VPS RAM — unbounded fetches for admin notification loops and metric aggregations are the highest-risk items.

**How to apply:** Flag any `list_documents(USERS, ...)` call not scoped to a specific user; flag any N+1 pattern where a loop runs a DB query per element; flag LIMIT > 1000 in non-batch-cleanup contexts.
